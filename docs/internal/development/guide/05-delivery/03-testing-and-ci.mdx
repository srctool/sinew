# 03 - Testing and CI

<KotlinOnly>

## 1. Why {#kotlin-1-why}

Sinew's tests run in `commonTest` wherever possible, and on each platform where behavior differs: secure storage, crypto, biometrics, the network checker, engine errors. CI has to run all of them, enforce the dependency graph and the ABI, and prove that production builds carry no devtools.

## 2. Shape {#kotlin-2-shape}

| Job | Runner | Runs |
|---|---|---|
| `jvm-android` | ubuntu | `./gradlew check` for android (host tests) and jvm: unit tests, `checkKotlinAbi`, `checkSinewGraph`, Detekt, Kover (80% floor) |
| `android-device` | ubuntu + emulator (Gradle Managed Devices) | instrumented tests: Keystore, Tink keyset loss, biometrics with an emulator fingerprint, the network checker |
| `ios` | macos | `./gradlew iosSimulatorArm64Test`, plus the Keychain, CryptoKit and biometric tests on a simulator, plus (from S5) an `xcodebuild` of the iOS sample |
| `web` | ubuntu | `./gradlew wasmJsBrowserTest` in headless Chrome |
| `devtools-gating` | ubuntu + macos | builds the production variants and fails if any non-no-op `com.srctool.sinew.devtools` class is present, and checks that the merged real ABI dumps equal the no-op dump (APK via `apkanalyzer`, the iOS framework via `nm`, desktop and web bundles by class and symbol listing) |
| `publish` | macos, on tags | see [Publishing](/guide/delivery/publishing) |

| Rule | Why |
|---|---|
| Test first by default. A test written after the code must be seen failing once. Bug fixes are always test-first. | The base testing rules |
| 80% line coverage per module, measured by Kover on the JVM run | The floor from the base note |
| Every job uses the Gradle build cache and the configuration cache | Four targets make the build slow otherwise |
| The web job is required, unlike Camouflage's | Sinew's web code is mostly plain Kotlin/Wasm. The Compose modules (`-l10n`, `-viewmodel`, `-camouflage`, `-devtools-ui`) are tested on web too, but their web screenshots aren't tested |

## 3. API {#kotlin-3-api}

Gradle tasks CI calls: `check`, `checkKotlinAbi`, `checkSinewGraph`, `koverVerify`, `iosSimulatorArm64Test`, `wasmJsBrowserTest`, `checkDevToolsGating` (a custom task wrapping the artifact checks), `publishAndReleaseToMavenCentral`.

## 4. Build steps {#kotlin-4-build-steps}

1. The `jvm-android` job at S0, with everything that runs on the JVM.
2. `ios` and `web` jobs at S0, on placeholder tests.
3. `android-device` at S4, when secure storage and biometrics exist.
4. `devtools-gating` at S7.

**Done when**
- [ ] All jobs are green on `main`, and the gating job fails on a branch that adds the real devtools to the production variant.

## 5. Edge cases {#kotlin-5-edge-cases}

| Case | Decided behavior |
|---|---|
| A flaky emulator biometric test | It's retried once by the job. Twice flaky in a week means it's fixed or quarantined, never ignored. |
| Coverage drops below 80% on a module | `koverVerify` fails the job. |

:::info[Decided by default (revisit during implementation)]

- **The web job is required** for Sinew. Unlike Camouflage, Sinew's web code doesn't depend on Compose web's Beta status.

:::

<DartOnly>

## 1. Why {#dart-1-why}

CI has to run the pure-Dart tests on the VM and in Chrome, the Flutter tests, the plugin integration tests on Android and iOS, the graph and publish checks, and the devtools gating proof.

## 2. Shape {#dart-2-shape}

| Job | Runner | Runs |
|---|---|---|
| `analyze` | ubuntu | `melos run analyze`, `melos run format`, `melos run graph`, `melos publish --dry-run` |
| `test` | ubuntu | `melos run test` with coverage, an 80% line floor per package (lcov) |
| `web` | ubuntu | the pure-Dart packages with `dart test -p chrome`; `flutter build web --wasm` for the example |
| `android` | ubuntu + emulator | `integration_test` for `sinew_security` (biometrics, Keystore), `sinew_storage`, the network checker |
| `ios` | macos | the same integration tests on a simulator, plus an iOS build of the example |
| `desktop` | macos, windows, ubuntu | builds the example; secure storage smoke tests per OS |
| `devtools-gating` | ubuntu + macos | production release **and profile** builds for Android, iOS and web, failing if the devtools marker string appears in the compiled output; a staging build must contain it |
| `publish` | ubuntu, on tags | see [Publishing](/guide/delivery/publishing) |

| Rule | Why |
|---|---|
| Test first by default; a test written after the code must be seen failing once; bug fixes test-first | The base testing rules |
| 80% coverage floor per package | The base floor |
| `--fatal-infos` on analysis | Lints are part of the API's quality on pub.dev |

## 3. API {#dart-3-api}

Melos scripts CI calls: `analyze`, `format`, `graph`, `test`, `publish --dry-run`. Plus the Flutter commands in the table.

## 4. Build steps {#dart-4-build-steps}

1. `analyze` and `test` at S0.
2. `web` and `desktop` at S0, on placeholder tests.
3. `android` and `ios` at S4, when security and storage exist.
4. `devtools-gating` at S7.

**Done when**
- [ ] All jobs are green on `main`. The gating job fails on a branch that removes the `const` from `DevToolsGate.enabled`.
- [ ] A `gen-l10n` check fails if the committed `sinew_l10n` output differs from a fresh generation.

## 5. Edge cases {#dart-5-edge-cases}

| Case | Decided behavior |
|---|---|
| A flaky emulator biometric test | Retried once. Repeated flakiness is fixed or quarantined, never ignored. |

:::info[Decided by default (revisit during implementation)]

- **Desktop jobs on all three OSes**, because `flutter_secure_storage` uses a different keychain on each.

:::
